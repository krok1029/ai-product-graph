# 願景

## 一句話定位

讓使用 AI agent 持續開發的專案，能追溯需求與成果、理解變更影響，並在換對話接手時繼續工作。

## 問題

產品想法通常一開始都很模糊。現有專案管理工具擅長追蹤任務，但不擅長保存任務背後的產品理由。

常見問題：

- 產品目標和 tickets 分離。
- Tickets 失去決策背景。
- 程式碼變更和使用者需求脫節。
- AI agent 不知道一個任務為什麼重要。
- 團隊很難從一個功能追溯到最初想法、release 和後續回饋。

## 解法

建立一個 MCP-first 的 AI 產品開發系統：

- 透過結構化 AI 對話釐清模糊想法。
- 把產品思考整理成 Product Brief。
- 從 brief、tickets、程式碼、PR 和回饋中萃取 Project Knowledge Graph。
- 依 Product Brief → Milestone → Spec → Ticket 拆解可獨立驗證的工作，並自動保存規劃關係。
- 以規劃內容版本分辨真正變更與重新確認，沿用仍有效的交付。
- 將驗收證據、使用者決策與後續工作連起來，降低重做與重複解釋。
- 給 coding agent 足夠的上下文，讓它能更安全地實作。

## 這個產品是什麼

- 給 AI agent 使用的 MCP 產品規劃 server。
- 專案知識圖譜。
- Ticket 生成系統。
- Coding agent 的上下文層。
- 既有 PM 和開發工具的整合層。

## 初期不是什麼

- Jira、Linear 或 Plane 的完整替代品。
- 完整團隊管理套件。
- 排程或甘特圖工具。
- 通用 mind map 工具。
- 單純的 code agent。
- UI-first Web app。

## 成功標準

本機主流程已實作；後續需驗證它能讓持續開發更容易管理：

1. 從原始想法產生有範圍與退出條件的規劃，並完成至少一條實作到使用者驗收的追溯鏈。
2. 新增需求時保留仍適用的 Ticket、計畫與驗收；真正修改規格時準確指出並阻擋過期來源。
3. 新對話能從正式資料還原目前工作、待接受結果、阻塞與下一步。
4. 記錄耗時、重複確認及人工修正，先建立基準，再比較同類情境；不以生成速度或紀錄數量代表產品價值。

後續階段與驗證界線見 [roadmap](08-roadmap.md)。
